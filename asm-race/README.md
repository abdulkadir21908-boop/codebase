# DUST RUNNER

A 3D racing game written entirely in x86-64 assembly. No C, no libc, no
libraries, no runtime — the whole thing is `car.asm` and it talks to the kernel
through raw syscalls. The build is `as` and `ld`, nothing else.

```
./build.sh                  # as + ld -> ./car
./run.sh                    # build and play
./check.sh                  # static checks
./selftest.sh               # prove the static checks actually fire
./all.sh                    # everything: build, checks, 3000 frames, a full race
```

## What it is

The renderer is a software pseudo-3D perspective projection into a 128-slice
depth buffer, rasterised into a linear RGB framebuffer and then pushed to the
terminal with ANSI truecolour half-blocks (`ESC[38;2;r;g;bm`, `ESC[48;2;r;g;bm`
and U+2580 ▀). One character cell carries two pixel rows, so a 100×30 terminal
is a 100×60 image. Per-slice fog, a sky gradient with clouds and a sun, hills
and curvature, kerbs, lane markings, roadside props and other cars are all
computed from the track data, not drawn from sprites.

```
car.asm      the game (about 4800 lines)
font.inc     the 5x7 bitmap font, generated by tools/genfont.mjs
```

## Controls

```
UP / W      accelerate          DOWN / S     brake
LEFT / A    steer left          RIGHT / D    steer right
P           screenshot          R            restart
Q / ESC     quit
```

Command line:

```
./car --frames 600              headless smoke test: 600 frames, no input needed
./car --seed 7                  pick a different track
./car --cols 100 --rows 30      force a screen size instead of asking the tty
./car --demo 9300               start 9300 m in, at 60 m/s
./car --shot out.ppm            render one frame to a PPM
./car --help
```

`--frames` holds the throttle down, because headless there is no keyboard to
press it with. It does so through a `sticky_throttle` flag that `poll_keys`
re-asserts every frame — setting `key_up` once does nothing, because `poll_keys`
clears all four key flags at the top of every frame.

`--frames` also fixes the step at the 5 ms minimum, so a headless run simulates
at 200 fps of game time no matter how fast the machine is. 900 frames is 4.5 s of
game time, of which the first 3 s is the countdown.

## How it is put together

Everything is one file, in this order: syscall wrappers, fixed-point maths,
`rng`, framebuffer primitives, text, output buffering, track generation,
physics, collisions, the HUD, the renderer, a PPM writer, terminal raw mode,
key input, and `_start`.

Fixed point is 16.16 throughout (`FP` = 65536). The maths helpers all follow
one convention, which the checkers enforce:

```
mul16(a=edi, b=esi) -> eax        (a*b)>>16
div16(a=edi, b=esi) -> eax        (a<<16)/b
scale_dt(v16=edi, dt16=esi) -> eax
seg_at(s16=edi) -> eax           segment index for a distance
elev_at(s16=edi) -> eax          road elevation at a distance
fog_amt(z16=eax) -> eax          0..256
lerp_color(a=edi, b=esi, t=ecx 0..256) -> eax
```

## Two things worth knowing about the environment

**`rep stosd` is not reliable.** On the WSL1 kernel this was developed on,
`rep stosd` consumes the count but runs the body exactly once, so every block
fill silently painted a single pixel. `fill32` is an explicit `dec ecx; jnz`
loop instead; it behaves the same on every machine.

**`.bss` is not zeroed here.** The anonymous part of the writable segment comes
up holding leftover data, so `clear_fb` runs at startup and nothing in the game
depends on the framebuffer starting clean.

## Verification

Static checks (`./check.sh`, source in `tools/asmcheck.py`):

| check      | what it catches |
|------------|-----------------|
| `width`    | a 64-bit load or store naming an object narrower than 8 bytes, which silently pulls in — or overwrites — its neighbour |
| `divloop`  | a divide loop that converts the remainder in `al` and then tests `eax`, so the loop never terminates |
| `muldiv`   | a helper returning its result in `eax` fed straight into another helper that reads `edi` |
| `argsites` | a maths helper called without its documented argument registers written in the same basic block |
| `argbody`  | a helper that does not actually read the registers it documents; `emit_sgr` read its colour out of `esi` while every call site passed `ecx`, so every background SGR carried whatever stale pointer `out_num` left behind |
| `layout`   | a `.space` whose size expression does not evaluate, or two labels on one address |

`argsites` and `argbody` are two halves of one contract: the first proves the
caller sets the argument registers, the second proves the callee reads them, so
caller and calleer cannot quietly disagree about which register an argument
travels in.

`./selftest.sh` feeds each one a deliberately broken `car.asm` and requires it
to complain, then requires the real file to pass. A checker that cannot fail is
worse than no checker.

Runtime checks:

```
./run.sh --frames 3000                     headless, must exit 0
python3 tools/playcheck.py raw.raw 100 30 --expect-finish
node tools/ansi2png.mjs raw.raw out.png 100 30 40 6   frame 40 as a PNG
node tools/ansi2png.mjs raw.raw out.png 100 30 40 6 0,25,40,5   a cropped HUD
node tools/hudread.mjs raw.raw 100 30 40 4 53 12 2 4 fff3c0  "175"
node tools/hudtext.mjs raw.raw 100 30 40 4 25 40 9         a region as ASCII
node tools/ansi2gif.mjs raw.raw out.gif 100 30 0 150 6 6    an animated GIF
node tools/ansimap.mjs raw.raw 100 30 40                    frame 40 as ASCII
node tools/framediff.mjs raw.raw 100 30 39 40               what changed
node tools/framecount.sh raw.raw                            cells and SGRs per frame
```

`playcheck.py` is the one that matters most, and it exists because a rendered
frame proves nothing about the simulation. For a long stretch of this program's
development every frame rendered perfectly while the car never moved a metre:
`now_ms` was computing `tv_sec*1000/1000000 + tv_nsec`, and the frame loop was
shifting `edi` when `div` reads `rax`, so every frame time came out as zero. It
asserts that consecutive frames actually differ, that the palette stays bounded
(a frame inventing colours means something is being painted out of a stale
register), and — with `--expect-finish` — that a run started 100 m short of the
line actually gets there.

`hudread.mjs` and `hudtext.mjs` read the HUD back out of a frame. A 5x7 glyph in
a half-block terminal is squashed 2:1 and is genuinely hard to read by eye, so
`hudread` matches the pixels against `font.inc` and prints the string the HUD was
drawn from, and `hudtext` prints the raw pixel grid. Most of the HUD layout bugs
found while writing this were found with those two, not by looking at PNGs.

The PNG/ASCII/GIF tools replay the escape stream exactly as a terminal would,
carrying SGR state across frames, and need `node` on the Windows side (there is
no `node` inside this WSL instance).

## Notes

- `car.asm` carries a second entry point, `probe`, linked with
  `ld -e probe -T car.o`. It runs the simulation headless with no terminal and
  prints the state the loop actually reaches (`state=`, `speed=`, `metres=`,
  `seconds=`) along with the frame times it computed. A picture cannot answer
  "did the car move"; this can, and it is what pinned down the `dt` bugs.
- `--shot` writes a PPM through `open`/`write`/`close`. It is implemented and
  assembles, but it could not be exercised in the sandbox this was written in:
  every `open`, including of `/proc/self/maps`, returns `EPERM` there.
- The rendering path was verified by replaying the raw ANSI output into PNGs;
  the PPM writer was not.
- Because one terminal cell is two pixel rows, HUD text drawn at scale 1 is
  vertically squashed 2:1. The big numbers are drawn at scale 2 (10x14 pixels =
  5x7 cells, pixel-exact) and the words around them at scale 1.
